SIDELINE PROCESSING COMPARISON
8 November 2026

Baseline: be80e558399d8b9287daa09ae00a7f5f1572a7e0 (earlier PR #303).
Candidate: this PR's exact-markup field, bunker-layer and screen caches.

Method
- Local Chromium, 390 x 844, device scale 2, CPU throttled 4x.
- The unchanged test/loadtest.js full-season fixture: 400 points,
  600 class responses, 300 league members, 500 blasts, 800 messages,
  1,200 moves and 500 grades.
- Four isolated runs in before / after / after / before order.
- 40 synchronous interactions per run: Tally, mark an out, change a
  Playbook call, Scout; repeated ten times with the load harness's names
  and calls. No profiler instrumentation in these comparison runs.
- Browser service workers blocked in this comparison so each run receives
  the requested source version. Offline behavior has its separate suite.
- Both versions kept 2,000 out records in memory, the working store and
  the recovery journal at the end of each run. No page errors.

Average processing time was about 20% lower in this local comparison.
The variation is substantial, and the second baseline overlaps the candidate.
This does not establish a 20% gain on all phones or all taps. An earlier
comparison of field reuse alone measured about 6%, with different run times.
These are local observations, not a guaranteed speed increase. Slow interactions
remain. These measurements cover local processing; account-server latency
and physical-device field testing are separate checks.

The optimization reuses parsed SVG by exact content, including a separate
bunker layer when paths change. Cached originals are cloned, bounded to
12 entries / 300,000 source characters and cleared on sign-out. Changes
to field geometry, paths, names or players still require the current SVG.
Save timing, recovery journals and the load/device thresholds are unchanged.
Up to three screen bodies (150,000 source characters total) are also kept
as inert originals; each return gets independent controls and current field
drawings. These pages are also discarded on sign-out.

The first final full run of field reuse alone failed Tally at 288.3 ms
against the unchanged 250 ms limit, despite green CI. That failure was not
discarded. After the screen reuse change, the focused load run passed with
Tally at 209.0 ms; slow warnings remained. The final full run is reported
in the PR with its exact commit.

One comparison attempt stopped after a local startup script failed to load
(guardVoiceSession was unavailable). It produced no candidate measurements.
The complete alternating block above was then run afresh, checking startup
before timing. All four included runs loaded correctly and had no page errors.

Regression checks cover unchanged-field parsing, changed paths/geometry,
fresh clones after live edits, cache limits, sign-out cleanup, scroll and
form behavior, screen reuse, tool search and immediate persistence. Phone Tally and tablet Scout
screenshots are included alongside this report.
